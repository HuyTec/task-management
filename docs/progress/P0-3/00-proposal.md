# P0-3 Proposal - Atomic Project Task Planning

## Status

- State: Proposed for review
- Production code changed: No
- Tests changed: No
- Depends on: P0-1 Auth and P0-2 Project Member authorization
- Out of scope: File/folder upload, work evidence, submit review, approval, Dashboard

## Problem observed in the current flow

Project Task creation currently uses multiple HTTP requests:

```text
POST /api/tasks
  -> POST /api/tasks/{taskId}/criteria for every criterion
  -> PUT /api/tasks/{taskId}/assignee when an assignee was selected
```

If criterion or assignment setup fails, the Task remains persisted in an incomplete state. The frontend detects this with `partiallyCreatedTaskId`, but recovery UI does not restore atomicity.

The generic create endpoint also accepts `projectId`, so a direct API caller can create a Project Task without the description, due date, acceptance criteria, or optional initial-assignment contract enforced by the React form.

## Goal

Provide one backend command that either creates the complete Project Task plan or creates nothing:

```text
Task + acceptance criteria + optional assignment = one transaction
```

Personal Task creation remains lightweight and separate.

## Recommended API boundary

### New atomic endpoint

```http
POST /api/projects/{projectId}/tasks
```

Suggested request:

```json
{
  "title": "Add refresh-session tests",
  "description": "Prove rotation, reuse rejection, logout and Redis outage behavior.",
  "priority": "HIGH",
  "dueDate": "2026-08-30",
  "criteria": [
    "Old refresh token reuse returns 401",
    "Redis outage returns 503"
  ],
  "assigneeUsername": "alice"
}
```

`assigneeUsername` is nullable. Null means the Task remains open for a MEMBER to claim.

### Existing endpoint

```http
POST /api/tasks
```

This endpoint remains for Personal Tasks. After frontend migration, passing a non-null `projectId` to it should be rejected so callers cannot bypass the Project Task contract.

The existing criteria and assignment endpoints remain available for authorized TODO-stage editing and reassignment. They are no longer used for initial Project Task setup.

## Service ownership

Recommended owner: `TaskWorkflowService` / `TaskWorkflowServiceImpl`.

Reason:

- It already owns Project Task authorization.
- It already owns assignment eligibility.
- It already owns acceptance-criteria mutation.
- Its class-level transaction can cover Task, criteria, and assignment persistence.
- Keeping the composite command here avoids duplicating workflow policy in the controller or frontend.

The controller should only validate the request and delegate. It must not orchestrate repository calls.

## Required invariants

1. Only Project OWNER or MANAGER can create a Project Task.
2. Authorization occurs before assignee lookup.
3. Description is required and non-blank for Project Tasks.
4. Due date is required and stays inside the Project date range.
5. At least one non-blank acceptance criterion is required.
6. Criteria order is generated by the server from list order.
7. Criteria content is trimmed and limited to 1000 characters each.
8. A request contains at most 20 criteria.
9. Optional assignee must be an active member of the same Project.
10. VIEWER cannot be assigned; OWNER, MANAGER, and MEMBER retain current eligibility.
11. New Task status is always TODO.
12. Initial assignment type is ASSIGNED and status is ACTIVE.
13. Any persistence failure rolls back Task, criteria, and assignment together.
14. The old generic endpoint cannot create an incomplete Project Task.

## Proposed Project lifecycle rule

Recommended creation states:

| Project status | Create Project Task |
|---|---:|
| PLANNING | Allow |
| ACTIVE | Allow |
| ON_HOLD | Reject |
| COMPLETED | Reject |
| ARCHIVED | Reject |

Rationale: PLANNING supports preparing work before activation; ACTIVE supports adding planned scope; ON_HOLD, COMPLETED, and ARCHIVED should not accept new work.

This is a product decision and should be approved before implementation.

## Validation contract

Suggested limits align with the existing UI and schema:

| Field | Rule |
|---|---|
| title | Required, trimmed, maximum 160 characters |
| description | Required, trimmed, maximum 2000 characters |
| priority | Required |
| dueDate | Required and within Project range |
| criteria | 1-20 entries |
| criterion | Required after trim, maximum 1000 characters |
| assigneeUsername | Optional, maximum 255 characters |

The backend remains authoritative even though equivalent constraints exist in React.

## Transaction design

Inside one `@Transactional` service command:

1. Resolve current authenticated user.
2. Resolve their Project membership and require OWNER/MANAGER.
3. Validate Project lifecycle and date range.
4. Resolve optional assignee and reject VIEWER.
5. Build and persist Task as TODO.
6. Build and persist all criteria with server-generated positions.
7. Persist the optional ACTIVE assignment.
8. Return the created Task response.

Validation and relationship lookup should happen before the first write where practical. Database exceptions after writing still roll back the whole transaction.

## Frontend change

For a Project Task, `TaskCreatePage` sends one request to the new endpoint. It no longer loops over criteria or calls `assignTask()` during initial creation.

The following partial-state UI can then be removed for this flow:

```text
partiallyCreatedTaskId
"The task was created, but its workflow setup is incomplete"
```

Personal Task creation continues using the existing request.

## Test-first plan

### Expected passing foundations

- OWNER/MANAGER project authorization.
- Existing assignment rejects VIEWER.
- Existing criteria and assignment workflows remain editable in TODO.

### New red tests

1. Composite create persists Task, ordered criteria, and optional assignment.
2. MEMBER and VIEWER are rejected before assignee lookup.
3. Missing/blank criteria are rejected before persistence.
4. Due date outside Project range is rejected.
5. Assignee from another Project is rejected.
6. VIEWER assignee is rejected.
7. Repository failure during criteria or assignment leaves no Task after rollback.
8. Generic `POST /api/tasks` rejects non-null `projectId`.
9. Frontend Project flow makes exactly one create command.

At least one integration test should use real JPA repositories to prove rollback. Mockito interaction tests alone cannot prove transaction rollback.
